# 生成中文智能体技能文档的提示词(v2)

> 适用场景:把一个业务流程整理成可复用、可交接、可执行的智能体技能包。
> 目录风格:中文目录 + `SKILL.md` 主流程 + 子智能体 + 技能 + 脚本。
> 核心原则:脚本在"生成阶段"提前写好并验证,"运行阶段"智能体只调用,不重新生成。
> 使用方式:**第一节完整版是唯一来源**,第二、三节是从它裁剪出的快捷版,修改规则时只改第一节,再同步裁剪版。

## 版本记录

| 版本 | 改动 | 原因 |
|---|---|---|
| v1 | 初版 | - |
| v2 | 1. 区分"生成阶段/运行阶段";2. 新增"清单确认"检查点;3. 缺失信息统一处理为"默认假设/需要用户补充";4. `主控流程.md` 拆分条件量化;5. 新增阶段间交接契约表;6. 必含项允许写"本技能不涉及";7. 脚本新增统一退出码、强制 dry-run、默认拒绝覆盖、机器可读摘要、编码与依赖约定;8. 新增 `校验技能包.py`、验收样例、变更记录;9. 精简版/补脚本版改为从完整版裁剪 | 消除内部矛盾、减少截断与凑字数、提高多智能体交接稳定性 |

---

## 一、完整版(复制下面整个代码块给 AI)

````text
你是一名资深智能体技能包架构师。请根据我提供的业务材料,生成一套中文智能体技能文档包。

# 0. 工作方式(先读这一节)

## 0.1 两个阶段,规则不同

| 阶段 | 谁在做 | 允许做什么 |
|---|---|---|
| 生成阶段 | 你(现在) | 编写文档、编写并验证脚本 |
| 运行阶段 | 日后执行技能的智能体 | 只能调用已有脚本;不得重新生成同名脚本 |

运行阶段只有在"脚本缺失、接口变更、用户明确要求修复"三种情况下才可修改脚本,且必须先说明原因、改后重新验证、同步更新脚本说明。

## 0.2 先确认清单,再生成文件(必须执行)

不要一次性输出整包。按两步走:

**第一步:只输出"设计清单",然后停下来等用户确认**,清单包含:
1. 技能名称与一句话目标;
2. 阶段列表(阶段名、产出物);
3. 子智能体列表与分工;
4. 技能文档列表;
5. 脚本列表(每个脚本一句话用途、是否计费、是否有副作用);
6. 人工确认点列表;
7. 默认假设(材料缺失处你采用的方案);
8. 需要用户补充的信息。

**第二步:用户确认后,再按第 9 节顺序逐个生成文件。** 若内容较多,分批输出并说明已完成/未完成的文件,不要因篇幅省略文件。

## 0.3 缺失信息的统一处理规则

- 用户材料中没有的信息,**不得编造**;
- 一律归入两个固定区块:"默认假设"(你先采用的合理方案)和"需要用户补充"(必须由用户提供的信息);
- 这两个区块只出现在设计清单和最终交付说明中;
- 技能包正文里不得出现"待定""稍后补充""大概可以"等不可执行表述;正文要么写明确规则,要么写"本技能不涉及"。

# 1. 最终目录结构

<技能根目录>/
  SKILL.md
  主控流程.md              # 可选,仅满足 3.1 的拆分条件才创建
  CHANGELOG.md             # 版本号 + 改动内容 + 改动原因
  子智能体/
  技能/
  脚本/
    脚本说明.md
    requirements.txt       # 无第三方依赖时写明"仅使用标准库"
    校验技能包.py          # 见第 6.4 节
    <业务脚本>.py
  assets/
    样例/                  # 最小样例输入 + 期望输出,见第 6.5 节
    (其他:词表、模板、静态资源)

说明:

- `SKILL.md`:技能入口和默认主控流程,供主控智能体读取。
- `主控流程.md`:可选拆分文件,不与 `SKILL.md` 写成重复内容。
- `子智能体/`:每个阶段或角色一份 Markdown,例如"寻企智能体A-舆情穿透专家.md"。
- `技能/`:每个可复用能力一份操作规范,例如关键词设计、数据采集、接口调用、评分规范、报告规范。
- `脚本/`:提前写好的 Python 脚本和 `脚本说明.md`。
- `assets/`:参考词表、模板、示例材料、验收样例。

# 2. 生成目标

你要生成的不是普通教程文档,而是一套可以被智能体直接执行的技能包。

文档必须满足:

1. 主控读完 `SKILL.md` 后,知道整体流程、阶段顺序、确认点、交接契约和产出物。
2. 子智能体读完对应文档后,知道该做什么、调用哪个技能文档、调用哪个脚本、输出什么格式。
3. 脚本文档写清参数化调用方式,智能体可以直接执行:
   python 脚本/xxx.py --参数 值
4. 业务知识、接口规则、校验规则、异常处理、红线都落在 Markdown 中。
5. 重复性、确定性、规则性工作交给脚本;判断、总结、解释、组织语言交给智能体。

# 3. SKILL.md 必须包含

`SKILL.md` 是技能入口,默认也是主控流程。至少包含:

1. YAML frontmatter:
   ---
   name: 技能英文名或短横线名
   description: 一句话说明技能用途、阶段、触发词
   ---

2. 技能定位:
   - 解决什么业务问题;
   - 什么时候触发;
   - 什么时候不适用;
   - 最终产出是什么。

3. 主流程表:
   | 阶段 | 调用对象 | 输入 | 主要动作 | 产出 | 人工确认点 |
   |---|---|---|---|---|---|

4. 阶段交接契约表(必须有,下游阶段开工前先按此表校验上游产出):
   | 上游阶段 | 产出文件(固定文件名或命名规则) | 必需字段/必需内容 | 校验方式(脚本或检查项) | 校验失败时 |
   |---|---|---|---|---|

   校验失败时的动作必须明确:退回上游重做 / 停下询问用户 / 标记失败后继续,三选一。

5. 人工确认点:
   - 每个高风险、计费、不可回滚、对外交付节点必须显式停下来询问用户;
   - 明确"用户确认后才能进入下一阶段"。

6. 执行规则:
   - 阶段顺序;
   - 可并行和不可并行的环节;
   - 失败处理原则;
   - 缺失数据处理原则;
   - 是否允许跳过确认点(默认不允许);
   - 是否允许真实调用计费接口(默认先 dry-run,确认后才真实调用);
   - 日志中是否允许出现账号、key、token 等敏感信息(默认不允许)。

7. 目录索引:
   - 列出每个子智能体、每个技能文档、每个脚本、可选主控流程文档的相对路径;
   - 所有链接使用相对路径,不使用本机绝对路径。

# 3.1 主控流程.md 什么时候才需要

默认不要单独创建。满足下列任一量化条件才拆出:

1. `SKILL.md` 超过 300 行;
2. 阶段数超过 6 个;
3. 子智能体 + 技能文档总数超过 12 份,且主控需要维护全局失败恢复流程。

拆分口径:

- `SKILL.md`:入口、触发词、总流程表、交接契约表、确认点、执行规则、目录索引;
- `主控流程.md`:主控的详细启动步骤、阶段调度细节、全局异常处理与恢复流程;
- 两者的流程结论必须一致,不得重复维护两套口径;交接契约表只保留在 `SKILL.md`。

# 4. 子智能体文档必须包含

每个 `子智能体/*.md` 写成可独立执行的任务说明书,包含:

1. 角色定位;
2. 触发条件;
3. 上游输入(含按交接契约表做的输入校验步骤);
4. 本阶段目标;
5. 执行步骤;
6. 需要引用的技能文档;
7. 需要调用的脚本;
8. 每一步的输出字段或文件格式;
9. 质量校验规则;
10. 异常处理;
11. 禁止事项;
12. 交接给下一阶段的内容;
13. 需要用户确认的事项。

必须能回答:我现在拿到什么?按什么顺序做?读哪份技能文档?调用哪个脚本、参数是什么?产出文件叫什么?哪些情况必须停下来问用户?哪些情况不能自动继续?

某一项确实不适用时,写"本技能不涉及",不要编造内容。

# 5. 技能文档必须包含

每个 `技能/*.md` 写成操作规范,包含:

1. 目标;
2. 适用场景;
3. 不适用场景;
4. 输入条件;
5. 输出结果;
6. 执行流程;
7. 业务规则;
8. 接口、数据库、文件或外部系统规则;
9. 字段映射;
10. 校验规则;
11. 异常处理;
12. 边界情况;
13. 安全和日志要求;
14. 可复用示例;
15. 与脚本的调用关系。

不适用的项写"本技能不涉及"(例如纯文件处理技能无需写分页规则、错误码),不要为凑齐条目而编造。

如果技能对应 API、数据库、浏览器操作、文件处理或模型调用,必须写清:请求方式、必填参数、可选参数、默认值、返回结构、错误码、重试规则、分页规则、超时规则、成功样例、失败样例、输出文件格式。

# 6. 脚本要求

脚本在生成阶段写好并验证,运行阶段只调用。

## 6.1 基本规则

1. 使用 Python 标准库或用户明确允许的第三方库;第三方库必须列入 `脚本/requirements.txt` 并固定版本。
2. 使用 `argparse` 提供命令行参数,每个脚本必须支持 `--help`。
3. 所有路径、日期、ID、关键词、阈值、输出文件名等可变内容都要参数化。
4. 默认调用形式:
   python 脚本/xxx.py --input "输入文件.xlsx" --output "输出文件.xlsx" --date-from "2026-01-01" --date-to "2026-01-31"
5. 不得硬编码:本机绝对路径、业务专属日期、业务专属 ID、每次都会变的文件名、只适合一次任务的关键词。
6. 必须有默认值时,在脚本说明中写清默认值和覆盖方式。
7. 文件读写统一使用 UTF-8;读写 Excel/CSV 时写明中文编码处理方式(CSV 输出建议 `utf-8-sig`),并在脚本说明中注明。

## 6.2 安全与副作用约束

1. **计费接口、写外部系统、删除或覆盖数据的脚本,必须提供 `--dry-run`**(只校验输入、打印将要执行的动作与预估数量,不产生真实调用和副作用)。无副作用的脚本可选。
2. **默认拒绝覆盖已有输出文件**,需要显式传 `--overwrite` 才覆盖。
3. 敏感信息不得写入日志。凭据策略由用户指定;公开仓库必须使用环境变量或占位符,内部私有技能可按用户要求写入受控配置,但日志不得打印明文凭据。

## 6.3 输出与退出码约定(所有脚本统一)

**退出码:**

| 退出码 | 含义 | 智能体应对 |
|---|---|---|
| 0 | 全部成功 | 进入下一步 |
| 1 | 参数或输入文件错误 | 修正参数后重跑,不算失败重试 |
| 2 | 部分失败(有失败行) | 读取失败清单,按脚本说明决定重试或交给用户 |
| 3 | 外部接口/系统失败 | 按重试规则重试;超过次数则停下询问用户 |
| 4 | 被安全规则拦截(如未加 `--overwrite`、缺少确认) | 不得自行绕过,询问用户 |

**输出稳定性:**

1. 成功时写完整输出文件;
2. 失败时不得伪造成功结果,失败行留空或明确标记,并写入失败清单;
3. 不得用 0、空值、"成功"等假数据掩盖真实失败。

**机器可读摘要(每个脚本结束时必须输出):** 写入 `<输出文件名>.summary.json`,同时在标准输出打印一行摘要。字段:

```json
{
  "status": "success | partial | failed",
  "dry_run": false,
  "total": 0,
  "success": 0,
  "failed": 0,
  "skipped": 0,
  "output_files": [],
  "failed_list_path": "",
  "started_at": "",
  "finished_at": ""
}
```

智能体读取该摘要判断下一步,不靠解读日志文本。

## 6.4 校验技能包.py(必须生成)

生成 `脚本/校验技能包.py`,用脚本完成确定性自检,至少检查:

1. 所有 Markdown 相对链接指向的文件存在;
2. `SKILL.md` 的 frontmatter 含 `name` 和 `description`;
3. 子智能体文档含第 4 节的 13 项章节标题,技能文档含第 5 节的 15 项章节标题;
4. 文档与脚本中没有本机绝对路径(如 `C:\`、`/Users/`、`/home/`);
5. 没有疑似明文密钥(如 `password=`、`token=`、`api_key=` 后跟长字符串);
6. `脚本说明.md` 中列出的脚本都真实存在,且 `脚本/` 下的脚本都在说明中有记录;
7. 文档中不含"待定""稍后补充""大概可以"。

参数:`--root <技能根目录>`;发现问题时退出码 2 并列出清单,全部通过退出码 0。

## 6.5 验收样例

`assets/样例/` 下必须放:

1. 一份最小输入样例(每个关键脚本至少一份);
2. 对应的期望输出样例;
3. `样例说明.md`:写清用哪条命令跑、期望得到什么、如何比对。

"最小验证"以此样例为准。涉及计费或外部系统的脚本,样例用 `--dry-run` 验证。

# 7. 脚本说明文档

`脚本/脚本说明.md` 必须包含:

1. 脚本总表:
   | 脚本 | 用途 | 输入 | 输出 | 是否计费 | 是否有副作用 | 是否可重试 | 支持 dry-run |
   |---|---|---|---|---|---|---|---|

2. 每个脚本的详细用法:
   python 脚本/xxx.py --参数 值

3. 参数表:
   | 参数 | 必填 | 类型 | 默认值 | 说明 |
   |---|---|---|---|---|

4. 输出字段说明(含 `.summary.json`);
5. 退出码说明(沿用 6.3 的统一约定,有脚本特有情况再补充);
6. 失败处理;
7. 重试方式;
8. 断点续跑说明;
9. 是否覆盖已有文件、如何 `--overwrite`;
10. 安全注意事项;
11. 依赖安装说明(对应 `requirements.txt`);
12. 最小验证命令(对应 `assets/样例/`)。

# 8. 安全规则

1. 所有内部链接使用相对路径。
2. Markdown 使用 UTF-8。
3. 不在日志中打印账号、密码、token、key、签名串等敏感值。
4. 如果凭据来自技能文档、配置文件或环境变量,必须写明来源。
5. 计费接口、不可逆操作、对外发布、覆盖源数据前,必须先请求用户确认。
6. 浏览器自动化遇到验证码、滑块、扫码、二次验证时必须停止,交给用户处理。
7. 不要在公开仓库或博客文档中写入真实账号、密码、token、key。

# 9. 生成流程

先完成第 0.2 节第一步(设计清单)并等待用户确认,然后按以下顺序工作:

1. 阅读用户业务材料,提取真实流程,不要凭空发明步骤。
2. 编写 `SKILL.md`,默认在其中写清主控流程和交接契约表。
3. 仅当满足 3.1 的量化条件,才拆出 `主控流程.md`。
4. 编写所有 `子智能体/*.md`。
5. 编写所有 `技能/*.md`。
6. 编写所有业务脚本 `脚本/*.py`、`requirements.txt`、`校验技能包.py`。
7. 编写 `脚本/脚本说明.md`。
8. 准备 `assets/样例/` 和 `CHANGELOG.md`(首版记为 v1.0)。
9. 如果能执行本地验证,依次运行并报告结果:
   python -m py_compile 脚本/*.py
   python 脚本/校验技能包.py --root .
   python 脚本/<每个脚本>.py --help
   各关键脚本的样例命令(或 --dry-run)
10. 无法执行验证时,明确写"未验证"并列出需用户执行的命令,不得声称已通过。
11. 最后输出:
    - 生成的目录树;
    - 每个文件的一句话说明;
    - 主流程快速启动命令;
    - 脚本调用示例;
    - 已知限制;
    - 默认假设;
    - 需要用户补充的信息。

# 10. 写作风格

1. 使用中文。
2. 使用短句、表格、编号步骤。
3. 不要写成营销文案,不要写空洞原则。
4. 每条规则都要能执行或验证。
5. 每个文档都要能独立指导智能体工作。
6. 禁止"稍后补充""待定""大概可以"等不可执行表述(缺失信息的处理见 0.3)。
7. 用户材料中没有的信息不要编造。

# 11. 我的需求材料

【技能名称】:
【一句话目标】:
【触发词】:
【输入是什么】:
【最终输出是什么】:
【业务阶段】:
【子智能体划分】:
【需要调用的系统或接口】:
【已有脚本】:
【数据来源】:
【人工确认点】:
【禁止事项】:
【输出格式要求】:
【凭据策略】:
【部署环境】:

如果某些材料为空,按 0.3 节处理:先列入"默认假设"和"需要用户补充",并在设计清单中请用户确认。
````

## 二、精简版(从完整版第 0、1、3、6、9 节裁剪)

适合发给对话式 AI、不想贴太长时使用。规则冲突时以第一节为准。

````text
请帮我生成一套中文智能体技能包。

先只输出"设计清单"(技能名、阶段、子智能体、技能文档、脚本清单、人工确认点、默认假设、需要我补充的信息),等我确认后再生成文件。

CHANGELOG.md

技能/

assets/(含 样例/)
````

## 三、给技能包补脚本时的专用提示词(从完整版第 6、7 节裁剪)

技能文档已有,只需把某些步骤固化成脚本时使用。

````text
请为以下技能文档补充可复用 Python 脚本,放入 `脚本/` 目录。

要求:

1. 先阅读对应技能文档,提取固定流程、字段规则、校验规则和异常处理规则;文档没写清的规则列入"需要用户补充",不要自行编造。
2. 所有路径、日期、ID、关键词、阈值、输出文件名都用 argparse 参数,不写死一次性业务值。
3. 推荐形式:
   python 脚本/xxx.py --input "输入.xlsx" --output "输出.xlsx" --param "值"
4. 每个脚本支持 --help。
5. 统一退出码:0 成功 / 1 参数错误 / 2 部分失败 / 3 外部接口失败 / 4 被安全规则拦截。
6. 结束时输出 <输出文件名>.summary.json(status、total、success、failed、skipped、failed_list_path、output_files、started_at、finished_at)。
7. 成功时输出完整结果文件;失败时不伪造成功,失败行显式标记并写入失败清单。
8. 计费、写外部系统、删除或覆盖数据的脚本必须支持 --dry-run;默认拒绝覆盖已有输出,需 --overwrite。
9. 能断点续跑的脚本要支持断点续跑,并在说明里写清续跑方式。
10. 敏感信息不写入日志。
11. 文件统一 UTF-8;CSV 输出用 utf-8-sig;第三方依赖写入 requirements.txt 并固定版本。
12. 同步更新 `脚本/脚本说明.md`(总表、参数表、退出码、重试、续跑、覆盖行为、最小验证命令),并在 `assets/样例/` 补最小输入与期望输出。
13. 最后运行 python -m py_compile 脚本/*.py 和 python 脚本/校验技能包.py --root .,给出每个脚本的调用示例;无法执行的写"未验证"。
14. 在 CHANGELOG.md 追加版本号、改动内容、改动原因。
````
